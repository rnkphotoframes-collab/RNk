# MASTER DEVELOPMENT PROMPT — RNK PHOTO FRAMES

## 1. Project Overview

Build a complete, production-ready, premium photo frame business portfolio website for **RNK Photo Frames**, located in PodaturPet, Tiruttani, Tamil Nadu, India.

This must be a real, functional, database-connected application, not a static UI prototype.

The website must have two distinct areas:

1. **Public Customer Website:** Visitors can browse products, view images, sizes, prices, business details, and contact the business.
2. **Secure Admin Dashboard:** The authorized admin can manage products, return gift combos, categories, prices, images, banners, and customer enquiries.

Customers must have read-only access. Only the authenticated admin can create, update, disable, or delete catalogue content.

## 6. Product Data Model

Design a normalized PostgreSQL schema.

### Categories
Fields:
- id
- name_en
- name_ta
- slug
- description
- display_order
- is_active
- created_at
- updated_at

Seed the six requested categories:
- Photo Frames
- Return Gift Combos
- Customized Frames
- Birthday Frames
- Wedding Frames
- Other Gift Items

Allow the admin to assign a product to an appropriate category.

### Products
Fields:
- id
- name_en
- name_ta
- slug
- short_description_en
- short_description_ta
- description_en
- description_ta
- category_id
- original_price, nullable
- offer_price, nullable
- primary_image_path, nullable
- is_active
- is_featured
- display_order
- created_at
- updated_at

Use appropriate constraints and indexes. Store monetary values as PostgreSQL NUMERIC values with two decimal places, not floating-point numbers.

### Product Images
Fields:
- id
- product_id
- storage_path
- alt_text_en
- alt_text_ta
- display_order
- created_at

Support multiple images per product and designate a primary image. Deleting a product must handle its related records safely.

### Product Sizes and Prices
Create a separate table for products with multiple sizes.

Fields:
- id
- product_id
- size_label_en
- size_label_ta
- width
- height
- measurement_unit
- original_price
- offer_price
- is_available
- display_order
- created_at
- updated_at

Examples of sizes such as 4x6, 5x7, 8x10, and 12x18 inches may be offered as examples only. Do not assume these sizes are actually sold by RNK. The admin must be able to add any size and price.

Allow different prices for different sizes.

Validate that prices are non-negative and that an offer price, when present, is lower than its corresponding original price.

Avoid storing redundant size prices at both product and size level in a way that creates conflicting values. Define a clear pricing rule: size-specific prices take precedence when size variants exist; otherwise, use the product-level price.

### Return Gift Combos
Create a dedicated combo model or use a consistent shared product model with an explicit product type. Choose the implementation that provides clean validation and maintainability.

Combo fields must include:
- Combo name in English and Tamil
- Slug
- Description in English and Tamil
- Included items and quantities
- Original price
- Offer price
- Multiple images
- Availability
- Featured status
- Display order
- Created and updated timestamps

Support adding, editing, disabling, and deleting combos.

Allow an admin to describe the included gifts and quantities. If individual item prices are not provided, do not invent them.

### Enquiries
Fields:
- id
- customer_name
- phone_number
- product_id, nullable
- combo_id, nullable
- enquiry_type
- message
- status
- created_at
- updated_at

Possible statuses:
- NEW
- CONTACTED
- RESOLVED
- SPAM

An enquiry must be associated with the selected product or combo when applicable.

### Business Settings
Store configurable settings for:
- Business name
- Phone
- WhatsApp number
- Location
- English introduction
- Tamil introduction
- Logo
- Contact details
- Social links
- Default language
- SEO title and description

### Banner Management
Support:
- Banner image
- English heading and subtitle
- Tamil heading and subtitle
- CTA label and optional destination
- Active/inactive state
- Display order

Validate CTA destinations and prevent unsafe URL schemes. If multiple banners are active, define an explicit display order or active banner selection.

## 7. Secure Admin Authentication

Admin features:
- Email and password login
- Secure session handling
- Logout
- Protected admin routes
- Clear invalid-login messages
- Loading and error states
- Session expiry handling
- Password reset workflow if configured
- No public admin registration

Create the initial admin account through a documented secure setup procedure. Do not hardcode a real admin email or password into the source code.

A user who merely creates a Supabase account must not automatically gain admin privileges.

Implement a secure single-admin authorization strategy using trusted server-side authorization and database policies. Do not trust a role or admin flag supplied by the browser.

Never expose Supabase service-role credentials, database passwords, or other secrets in client-side code.

## 9. Image Upload and Storage

Use Supabase Storage for persistent image storage.

Requirements:
- Upload from desktop and mobile
- Support multiple images per product
- Support banner uploads
- Validate file types
- Enforce configurable file size limits
- Generate unique, safe object paths
- Display upload progress
- Show previews before saving
- Handle upload failures and retry safely
- Prevent unauthorized overwrites and deletions
- Use optimized image sizes and modern formats where supported
- Keep image metadata and storage paths consistent

Use a public read-only image bucket only when appropriate for published product and banner images. Enforce authenticated admin permissions for uploads and mutations. Keep private files in private buckets if introduced later.

Avoid leaving orphaned storage files when database changes fail or a product is deleted. Use a reliable cleanup strategy with appropriate failure handling.

## 10. Customer Catalogue Security

Customer access must be read-only.

Visitors can:
- View active categories
- View published products and combos
- View product images
- View available sizes and prices
- View business information
- Use phone and WhatsApp links

Visitors cannot:
- Create or modify products
- Change prices
- Upload or delete images
- Edit banners
- Modify business settings
- Read private admin data
- Access protected admin operations

Implement authorization in the database and trusted server-side layers, not merely by hiding admin buttons.

Configure PostgreSQL privileges and RLS policies for every exposed table. Ensure public users can read only the necessary published, active catalogue data. Restrict enquiries and business-setting mutations to the authorized admin or a validated server-side submission path.

Never ship a service-role key to the browser.

## 18. Development Workflow

Follow these steps in order:

1. Inspect the current repository before modifying anything.
2. Identify whether a project already exists and preserve useful existing code.
3. Establish the application architecture and database schema.
4. Create migrations, constraints, indexes, and security policies.
5. Implement authentication and authorization.
6. Build the public catalogue and product pages.
7. Build the admin dashboard and CRUD operations.
8. Implement persistent image uploads.
9. Add Tamil/English localization.
10. Integrate WhatsApp and phone contact links.
11. Implement responsive styling and accessibility.
12. Add tests and execute them.
13. Fix identified failures rather than hiding them.
14. Document setup and deployment.
15. Verify the complete workflow from a fresh installation.

Do not stop after creating the home page or a visual mockup.

Do not leave core features as TODOs, fake API responses, hardcoded product arrays, or nonfunctional buttons.

If external credentials are unavailable, implement the integration and clearly document the exact setup required. Never pretend that a live database, authentication, upload, or deployment has been tested when it has not.
